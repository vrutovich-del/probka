# Decisions

One line per technical decision and why. Newest at the bottom.

- Vite + React 18 + TypeScript strict — stack fixed by the project brief; React 18 per brief even though 19 is current.
- Plain CSS modules with design tokens as CSS variables, no UI kit — brief; tokens come from `design/…/Design System.dc.html`.
- vite-plugin-pwa for install and the offline shell (added in Phase 1 item 6) — brief.
- Dexie over IndexedDB for caps, photo blobs, badges, settings and the sync queue — brief; each table is added in the item that first needs it.
- @imgly/background-removal in a web worker for the cutout (added in item 2) — brief; it masks the original pixels instead of regenerating them. Its license is AGPL-3.0 (open question before item 2).
- `<input type="file" accept="image/*" capture="environment">` is the primary capture path, getUserMedia preview only behind a feature check — brief; most reliable on iOS Safari and Android Chrome PWAs.
- i18next with three JSON files generated from the strings table — brief.
- Phase 2 backend: Node 20, Fastify, PostgreSQL, Drizzle, Docker Compose on one Hetzner VM; Sign in with Apple/Google; guests stay local-only until linked — brief.
- react-router 7.18.3 in library mode — v8 requires React ≥19.2.7; 7.18.x is the newest line that supports React 18.
- A small `useT` hook over i18next instead of react-i18next — react-i18next is not on the approved library list.
- Flat translation keys (`keySeparator: false`) — the strings table has keys that are both a string and a prefix (`settings.delete` / `settings.delete.note`), which nested JSON cannot hold.
- TypeScript 7.0 for typechecking only; Vite transpiles — current stable; fall back to 6.0 if a tool needs the old compiler API.
- Two tsconfigs (app with DOM types, node for vite.config.ts), checked with `tsc -p` each — keeps browser code from seeing Node globals.
- Golos Text variable woff2 (weights 400–900), cyrillic and latin subsets only, self-hosted in `src/assets/fonts` — covers ru/en/uk in 60 KB; Vite hashes the files so the PWA precache can pick them up.
- Unnamed greys the prototype screens use (#565656, #232323, #2E2E2E …) are named by role in `tokens.css` — components never carry raw hex.
- Tab bar and rarity glyphs (⌂ ◎ ◈ ◉ ● ■ ▲ ◆ ★ ◌) are drawn as inline SVG — Golos Text has none of them, so fallback fonts would render them differently on iOS and Android.
- The app is a 390px column, #000 outside it, bg/base #0B0B0B inside, theme-color #0B0B0B — brief says centered on black; the token page defines the app ground.
- Settings live in a Dexie key/value table read before the first render — the chosen language shows immediately, with no flash of the wrong one.
- Git: the Claude Design handoff sits in `design/` as the root commit on `main`; each phase is a `phase-N` branch with one commit per item — every phase can be reviewed as a single diff.
- `scripts/strings-to-json.mjs` regenerates `en.json` from the design table with explicit rules for its shorthand rows, and checks `ru.json`/`uk.json` for missing keys, plural forms (via `Intl.PluralRules`) and placeholder drift — the table stays the source of truth for English, translations are hand-maintained.
- Language endonyms (English / Русский / Українська) are a code constant, not string keys — they read the same in every UI language, and a translator "translating" them would break the picker.
- The first-launch picker renders in a guess from `navigator.languages` and marks that row current; the pick still decides and is the only thing saved — the design's trilingual header needs a language to render in.
- ru/uk drafts use the formal вы/ви, following the design's own RU sample ("Найдите крышку и дайте ей дом") — switch to ты/ти is a global find-and-replace if the native review prefers it.
- Active tab = green + weight 600 + a 4px dot; the prototype changes color only, which the brief forbids as a sole cue.
- Tap targets: the tab bar's outer padding moved into the tab links (53px tall); back links get an invisible 48px hit area via `::after` — visuals stay pixel-identical to the prototype.
- `#root` is a flex column so a screen renders full-height with or without the tab shell — the first-launch picker sits outside the shell and must still center vertically.
- Cutout runs in our own Web Worker (`src/cutout/worker.ts`); the library's `proxyToWorker` only applies to WebGPU, and the ~5–20 s CPU inference must not block the UI.
- The library is asked for the mask only (`segmentForeground`, `image/x-alpha8`); the worker writes it into the alpha channel of the downscaled photo itself. Confirmed in its source that `removeBackground` does the same and never touches RGB — but owning the compositing gives us the bbox, rim colour and a sanity check (a mask covering <0.5 % or >99.5 % is treated as a failure → keep original).
- Model + ONNX runtime are mirrored into `public/cutout/` by `npm run cutout-model` (SHA-256-verified CDN chunks, trimmed resources.json), gitignored at ≈170 MB — the app never contacts IMG.LY at runtime, and the phone downloads only its own set: quint8 + wasm (56 MB) on CPU, fp16 + jsep (111 MB) where WebGPU exists. A WebGPU failure falls back to CPU automatically.
- The download starts when the + tab opens (`preloadCutout`) and the top photo's cutout starts the moment it is taken — both overlap with the time the child spends photographing.
- No caching layer of our own: in dev Vite answers `Cache-Control: no-cache` + ETag (304, body reused); the PWA service worker in item 6 gets a CacheFirst rule for `/cutout/`. The library itself does plain `fetch`.
- Vite copies `onnxruntime-web`'s 24 MB `.jsep.wasm` into `dist/assets` because ORT references it via `new URL(..., import.meta.url)`; the runtime overrides `wasmPaths` with `/cutout/`, so it is dead weight — exclude `*.wasm` from the precache glob in item 6.
- Photos: `original` is the file exactly as the camera gave it; `cutout` is a PNG at ≤1024 (the brief's permitted downscale) with RGB identical to that downscaled bitmap; `thumb` is a 256 px PNG for grids. Anti-aliased edge pixels lose a little RGB precision to canvas premultiplication — the only lossless alternative is a hand-written PNG encoder.
- Add-a-cap is a `/add/*` route stack under one layout route that owns the flow state; leaving to a tab drops it. Each step redirects to `/add/top` when its prerequisites are missing.
- Capture is `<input type="file" capture="environment">` (shutter) and a plain file input (gallery). Live preview via getUserMedia waits for HTTPS: phones on the LAN over http have no `mediaDevices`, so it could not be tested.
- Screen 15 in Phase 1 has one candidate, "Not identified yet" (the prototype's own label for unidentified caps): Confirm saves the cap unidentified, "None of these" opens manual entry. The "Saved as Unverified" note is omitted until the catalog exists.
- Country is a native `<select>` of ISO 3166-1 codes named by `Intl.DisplayNames` in the UI language — no typing for a child and nothing to translate; "Not sure" is the empty option.
- Condition defaults to Worn as in the prototype; the found-on date is a native date input defaulting to today (the prototype shows static text).
- 3D side texture: the band of the side cutout at 62–82 % of its bounding-box height (the prototype's fixed 68 %/20 % generalised to any photo); without a side photo the faces take the average colour of the top cutout's rim, sampled in the worker.
- The model's soft mask is cleaned before use (`cleanMask.ts`): one connected component is kept (biggest, most compact, nearest the centre), enclosed holes are filled, the inside is made fully opaque and the soft values survive only in a 2 px band at the contour. Reason: on an iPhone (CPU, quint8) a cap on light paper came back with speckles of background all over the frame, which also broke the 3D cap's bounding box. This touches the mask only, never the photo.
- Published on GitHub Pages at `/probka/`: `base` comes from `BASE_PATH` (set by the workflow, root locally), the router takes its basename from `import.meta.env.BASE_URL`, and a build plugin writes `404.html` (a copy of index.html, so deep links resolve on a static host) plus `.nojekyll`. Pages was chosen over a VM because Phase 1 has no backend and needs only HTTPS — which is what unblocks the camera, WebGPU and, later, the service worker on a phone.
- The deploy workflow mirrors the model itself (`npm run cutout-model`, cached by lockfile hash) instead of committing 160 MB: git history stays small and the published site still serves the model from its own origin.
- GitHub Pages cannot set COOP/COEP headers, so `SharedArrayBuffer` stays off and the CPU path runs single-threaded; the WebGPU path does not need them, which is where phones with WebGPU win.
- Work continues on `main` now that every push deploys to the phone; `phase-1` stays as the branch the first three items were written on.
- Dexie v3 keeps garage tiles in their own `thumbs` table: Safari stores IndexedDB blobs inline, so reading `photos` for a grid would load every original into memory. The grid reads only thumbs; a cap's photos load on its own screen.
- Live data via Dexie's `liveQuery` in a 15-line `useLiveQuery` hook — `dexie-react-hooks` is not on the approved list and the hook is trivial.
- Delete is immediate with a 5-second UNDO: the cap, its photos and its tile are removed in one transaction and held in memory; UNDO writes them back. Closing the app inside those 5 s makes the delete final, as the design implies.
- Garage sort/filter live in a tiny store outside React so coming back from a cap restores the same view ("back returns to the previous tab state"). Caps and Collections are two routes for the same reason.
- Collections in Phase 1: a brand's "known caps" = the distinct (brand · product) types the user has entered, so rings are always full — the honest number, per the brief. Grey catalog silhouettes and the maker line wait for the catalog.
- Cap detail shows only Delete of the prototype's Share · Edit · Delete row: sharing is Phase 2+ and editing is not in any Phase 1 item, and buttons that do nothing are fake data.
- Duplicate detection (screen 11) matches brand + product case-insensitively after manual entry; "Add as duplicate" bumps ×N and reveals the new photos without storing them, as the prototype does.
- Rarity tiers are rendered through one `TIERS` map (shape + colour + label) and every cap is Unrated until the catalog exists; the tier chips and rarity sort are wired but inert until then.
- Pilot readout: the review screen shows "4.7 s · gpu" under the buttons and each photo stores `cutoutMs`/`inferMs`/`device` — the Phase 1 acceptance asks for cutout times on both phones and there is no devtools on a phone. Remove or move to Settings after the pilot.
- The eleven labels the flow needs that appear on prototype screens but not in the strings table (`cam.gallery`, `manual.save`, `condition.foundOn`, …) went into APP_KEYS with their prototype line; four keys have no design copy at all (`processing.download`, `processing.offlineFirst`, `manual.fields.country`, `manual.countryNone`) and are marked "new" there for review.
- Badges are derived from the garage every time they are shown (`src/lib/badges.ts`), never stored: a deleted cap takes its progress with it and there is no second copy of the truth to keep in step. The reveal's unlock stack is the difference between the earned set before and after the write.
- All eight badges are listed, locked ones with their real progress — the brief forbids hiding what cannot be reached yet. Rare Hunter and Duelist honestly read 0 (nothing is Rare before the catalog, no duel has been played); Set Complete shows "Waiting for the catalog" instead of a counter, because only the catalog can say how many caps a set holds and "0/6" would be an invented number.
- Ten Finder, Half Hundred and Brand Loyal count duplicates, like the garage's own caps stat — otherwise the child would read "12 caps" on one screen and "9/10" on the other. Brand Loyal follows the brand with the most caps behind it and names it ("6/10 Zhiguli"), where the prototype hard-coded Zhiguli.
- Streak 7 has no rule in the prototype. A day is a calendar day on the phone's clock on which a cap was added (`createdAt`, which cannot be edited, rather than the found-on date, which can); the tile shows the longest run ever, so a badge once won is never taken back. Owner's choice.
- Screen 30 gets its three stat tiles (caps · brands · badges) because all three are honestly computable now; the nickname, avatar and friend code need an account, the Stats screen (32) needs the catalog, and Edit profile needs both, so they stay out. A tile is blank, not zero, until the garage has been read.
- Badge art is the owner's own eight images, cleaned by `scripts/clean-badge-art.py` (a one-off, not part of the build): a flat studio ground keyed out where the generator left one, blobs under 12 % of the biggest dropped, punched holes filled, then trimmed and squared to 256 px WebP — 144 KB for all eight, against 760 KB as PNG. The source files stay out of git at ~6.8 MB, as the cutout model does.
- A locked badge is its own art greyed and brightened (`grayscale(1) brightness(1.35) contrast(.85)`, 60 % opacity) rather than dimmed: several badges are drawn on a dark plaque that simply vanished into the tile when darkened. The tile's border and the line underneath say the same thing, so colour is never the only cue.
- The sample cap goes in through `saveCap` like any other, with no cutout run: both design files already carry alpha, so the stored cutout is the file itself and only the bbox and rim colour are measured, from a decoded copy that is thrown away. `analyse` moved out of the worker into `src/cutout/analyse.ts` so the main thread can measure without pulling the AGPL library in, and `CutoutResult.timing` became nullable — saying "nothing ran" beats inventing milliseconds the pilot report would then quote.
- The sample photos ship as lossless WebP, 426 KB against 719 KB as PNG: the alpha channel comes back bit-identical and the only pixels that differ are fully transparent ones, where RGB is invisible.
- The sample's brand and product are what is printed on the cap itself (Жигули · Пиво) and do not change with the UI language — a brand is data the child would type, not copy to translate. Its shape is Crown, against the prototype's own record, which says "Aluminium screw cap" while the photo beside it is a fluted crown cap. Found-on is the day it was loaded and the place is blank: the child found it nowhere, and "near school" would be invented.
- Pressing "Load a sample cap" twice says it is already in the garage instead of adding a second or bumping ×2 — it is a sample, not a find.
- `Row` renders a `<button>` when it is given `onClick` instead of `to`, so an action row in Settings looks and measures exactly like a navigation one.
- PWA via `vite-plugin-pwa` 1.3.0 in generateSW mode with `registerType: 'autoUpdate'`: no update prompt to write, translate or explain to a child, and a deploy lands on the next launch.
- The precache is the shell only — code, styles, fonts, icons, badge art, the sample photos: 27 entries, 1.3 MB. Two things are deliberately left out. `**/*.wasm`, because Vite copies onnxruntime's 24 MB jsep build into the bundle although the runtime comes from `/cutout/`. And the ONNX runtime chunks, because a phone loads either the plain or the WebGPU build, never both; they are CacheFirst at runtime instead, which halves the install and ends up in the same place after the first cutout.
- That runtime rule has to cover `assets/ort*.mjs` as well as `assets/ort*.js`: the worker loads the `.js` wrapper, which loads the `.mjs` beside it. Precaching only `**/*.js` would have left the cutout broken offline — caught by reading the generated `sw.js` against the built chunks.
- `/cutout/` is CacheFirst with a one-year expiry: the names are content-addressed, so a stale hit is impossible, and the 56–111 MB a phone downloads once must survive every later launch.
- The app icon is the mark from splash screen 01 — a primary ring around a dashed one — drawn by `scripts/make-icons.py` (a one-off, like the badge art). The maskable copy keeps the mark at 52 % of the side so a launcher's circle crop cannot clip it. The manifest holds one language and it is English: "Cap Garage" is the product's name, like the language endonyms.
- `index.html` references its icons through `%BASE_URL%`, not a relative path: a deep link is served from `404.html` at an arbitrary depth, where `./icons/…` would resolve against that path and 404.
- `navigator.storage.persist()` is asked for on every launch and its answer only logged. Phase 1 has no account and no server, so the garage is the only copy — but Chrome decides from how much the app is used, and a "no" today can become a "yes" later.
- A save that fails leaves the child on the condition screen with the photo still in memory and a line that says which failure it was — out of space, or anything else — instead of a toast that vanishes. `isStorageFull` walks the `cause`/`inner` chain because Dexie wraps the DOMException.
- The cutout preload waits for `navigator.onLine` and retries on the `online` event: asking with no network only produces a failure to log, and the service worker serves the files from its cache afterwards.
- Reduced motion, audited across the built stylesheet: the reveal's drop, tier pop and badge slide are swapped for a crossfade in React, the processing spinner slows to 3 s, the 3D cap stops auto-rotating and drops inertia, and the shutter's press transition is now switched off too. The only motion left is the Add button's background-colour fade, which moves nothing.
- Phase 2 auth: no Apple/Google and no e-mail (supersedes the brief line above) — an anonymous account is created on the device with a recovery code the parent keeps. Reason given by the owner: nothing identifying about a child is stored, and Sign in with Apple would cost 99 USD a year for a family pilot.
- Phase 2 backend moves to Cloudflare Workers + D1 + R2 on the free tier instead of Fastify + PostgreSQL on a Hetzner VM — free, nothing to administer, HTTPS included; Drizzle stays (it has a D1 driver). Photos go to R2, never into D1, and are served through the Worker so object URLs cannot be guessed.
- The creators must be able to restore or move an account to a new phone even when the recovery code is lost — an admin endpoint mints a one-time transfer code. Owner's explicit requirement, and the only safety net an account without e-mail has.
- Rarity keeps the brief's rule (a tier after 20 owners) rather than owner-assigned tiers — so every cap stays Unrated in a small circle, and the duel waits until there are enough collectors.
- The friends round is scoped to accounts, sync, invite codes, a read-only friend garage and the friends leaderboard; the duel is a separate round after friends work on real phones.
- The server is `server/`, its own npm package inside this repository rather than a workspace or a second repo: the Pages build runs `npm ci` at the root and must not pull wrangler and drizzle-kit down with it, while the app and the API still move in one commit and one review.
- Server dependencies are the four agreed ones (hono, drizzle-orm; wrangler, drizzle-kit) and nothing else. TypeScript is the root's own 7.0.2, found through npm's parent `node_modules/.bin`, and the Workers types are generated by `wrangler types` into a gitignored `worker-configuration.d.ts` instead of adding `@cloudflare/workers-types` — `npm run typecheck` regenerates them first, so a fresh clone needs no extra step.
- `wrangler types --strict-vars=false`: with strict vars the generated `Env` types `ENVIRONMENT` as the literal `"production"` from wrangler.toml, and comparing it with `"development"` becomes a type error — which is exactly the comparison the CORS rule is built on.
- CORS allows `https://vrutovich-del.github.io` always, and `http://localhost:5173` / `:4173` only when `ENVIRONMENT` is `development` — a value only `npm run dev` passes, because wrangler.toml hard-codes `production` for everything deployed. Checked against the live Worker: the site origin gets the header back, localhost does not.
- `/api/health` reports the Worker, D1 (a `select 1` through Drizzle, so the driver is on the tested path too) and R2 (`head` on a key nothing writes), with 503 when any of it is down. It also reports how many migrations wrangler has applied, read from `d1_migrations` and treating a missing table as zero: forgetting `d1 migrations apply --remote` after a deploy is the failure this scaffold is most likely to hit.
- Every route lives under `/api/`, even though the Worker has a domain to itself: it keeps one service-worker rule (`NetworkOnly` on `/api/`) honest whatever the API's address turns out to be, and leaves room for a custom domain later.
- No `[observability]` in wrangler.toml: Cloudflare's request logs would record more about the children than the brief's "error logs only" allows. `console.error` in the error handler plus `wrangler tail` when something needs watching.
- The migrations directory ships empty (item 1) — the first tables belong to accounts in item 2, and inventing a schema a round early would only have to be guessed twice. drizzle-kit writes the SQL, `wrangler d1 migrations apply` runs it: no database credentials live in the repository, and local and deployed databases take the same path.
- drizzle-kit's esbuild loader carries a moderate advisory (esbuild's dev server, GHSA-67mh-4wv8-2f99). It is kept: drizzle-kit only writes SQL on a developer's machine and never starts that server, and the only fix npm offers is drizzle-kit 0.18.1, from before the D1 support this project needs.
- The client learns the address from `VITE_API_URL` at build time (`src/api/client.ts`, `API_URL` / `hasServer()` / `apiFetch`), which the Pages workflow fills from the repository variable `API_URL`. Unset — which is every build until the owner sets it, and every `npm run dev` — means `hasServer()` is false and the app is the Phase 1 app. The variable is not a secret: the address ships inside the published JavaScript either way, which is why every route that touches data checks a token instead.
- An account is a nickname, one of six avatar shapes, a friend code and two secrets — nothing else. The device token and the recovery code are stored as SHA-256 hashes, so the database cannot be replayed against the API; the recovery code is returned once, at creation, and never again.
- The recovery code is 16 characters from a 32-letter alphabet with no 0/O/1/I (80 bits), the friend code 6 of the same (`K7M-4QZ`, the prototype's shape). One alphabet, because both are read off one phone and typed into another.
- `POST /api/accounts` is the only unauthenticated write, and it is rate-limited to 10 an hour per address — a household shares one address, so the window is generous. `/api/health` is 6 a minute: it is open to the internet and the free tier's daily budget is not a stranger's to spend. Both counters live in the isolate's memory, which costs nothing and is enough for a flood from one script; the friend-code guard that has to be reliable is counted in D1 instead (item 4).
- Nicknames are unique, case-folded, and "taken" is only ever learned from the account call's 409 — a live "is this free?" endpoint while the child types would be a way to walk the list of children.
- The prototype's green "✓ Available!" is therefore not shown: only the server can promise it. A nickname that passes the local rules gets no line at all, and the rules line stays under the field, as the prototype also has it.
- "Looks like a real name" blocks Continue instead of only warning, against the prototype, where it is one red line and the button still works. The brief's first rule is that no real name is stored, and a child reads past a warning.
- The server refuses a nickname with an `@` in it. An e-mail address is the one thing this project must never end up holding, and a child typing one into the only free-text field is a likelier accident than it looks.
- Account creation lives behind the parental gate (6 × 7), on screen 06's own button, exactly where the prototype puts it. The gate is not remembered: it is in-memory state in the prototype too, so a restart asks again — the conservative reading of "a parent must be there".
- Screen 04 (Apple / Google / guest) is not built and screen 37's sheet keeps only its text: the owner replaced both with an account the phone makes for itself. The sheet's own button is new copy (`link.cta`).
- The guest garage "merges" by staying exactly where it is: creating an account writes no caps and deletes nothing, and item 3's first sync uploads what is already on the phone. Nothing about the caps changes at the moment an account appears.
- Creating an account needs the network, and nothing else in the app does. Offline the button answers with one line and the child stays a guest — which is a working app, not a failure state.
- An account holder must not be told "you are a guest", so the Friends and Duel tabs stop showing the guest wall once there is an account: Friends shows its real (empty) list, and Duel says the duel comes later. Neither has a button that cannot work yet.
- The Worker's binding types come from `wrangler types`, but the client and the server still validate nicknames separately — two small copies of three rules, because sharing a module across two npm packages would mean a build step for the server that nothing else needs.
